# 传感器

传感器分**四条接入路径**（485 三条见 [sensors-paths.svg](../diagrams/sensors-paths.svg)；BLE 见下），均不占用 ESP32 GPIO：

1. **485 总线**（9600 8N1，与全车同一条）：水位（温湿度见下）
2. **继电器模块 DI 干接点**（X1-X8，内部上拉）：门磁、漏水
3. **蓝牙 → 车机 → MQTT**：OBD-II 车辆数据
4. **BLE 广播 → ESP32 蓝牙代理 → HA**：温湿度（纽扣电池类）

## 决策记录：温湿度为什么走 BLE 而不是 485

**背景**：市面便宜的纽扣电池温湿度计**只有 BLE 广播，没有 485 口**。
接 485 必须换工业 Modbus 温湿度——要走线、要 12V 供电、体积大、不好看，
正好抵消了选纽扣电池的初衷。

**决策**：温湿度走 **BLE + ESP32 蓝牙代理**，不挤 485 总线。
理由：

1. **职责分离**：485 总线的价值在**安全关键 + 执行器**（继电器、MPPT）。
   温湿度只用于环境监测/联动风扇，**不承担安全职责**，没必要为"统一"付走线代价。
2. **架构已预留**：HA 职责本就写明"多源汇聚（BLE 传感器、Frigate、车机）"
   （[n100-ha/design.md](../n100-ha/design.md)）。
3. **安全关键的温度另走 485**：低温禁充判定用 **MPPT `SolarBatTemp`**（走 485、硬线供电），
   与 BLE 温湿度彻底解耦。**纽扣电池没电是静默失效**，不能用于安全逻辑。

**代价（已实测）**：ESP32 同跑 485+MPPT+BLE 时 **Flash 53%→75%、RAM 33%→43%**，
偏紧。**推荐拆第二个便宜 ESP32 专跑蓝牙代理**，主网关保持干净。

详见 [ble-sensors.md](ble-sensors.md)。

## 传感器列表

| 传感器 | 接入方式 | 数量 | 用途 |
|--------|---------|------|------|
| 温湿度传感器 | **BLE（ESP32 蓝牙代理）** | 2 | 车内/储物仓环境监测，联动风扇 |
| 水位传感器 | RS485 / 干接点 | 2 | 清水箱、灰水箱液位 |
| 门磁传感器 | 模块 DI 输入口 | 2 | 中门/尾门状态，开门亮灯 |
| 漏水传感器 | 模块 DI 输入口 | 2 | 底盘/窗边漏水报警 |
| ELM327 OBD-II | 蓝牙 → 安卓车机 → MQTT → HA | 1 | 车辆数据（RPM > 500 → 行车充电，电压跳变 → 迎宾） |
| **电池温度（低温禁充）** | **MPPT 0xA3 轮询（非本模块）** | 1 | 安全关键，见 [energy/](../energy/) |
