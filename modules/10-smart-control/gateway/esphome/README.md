# ESPHome 固件

单 ESP32-S3 集中编译，packages 按区域拆分。生产固件 = `prod.yaml` 组装，测试件按阶段独立。

> 源文件以仓库为准；构建站点时 `.esphome/` 编译产物不随站发布。

### 手机控制面板（/dashboard）

自 2026-10-27 起，固件内置一个**自包含手机控制面板**，复刻 RV Dashboard（React）的深蓝
FORAGER 主题，但彻底零依赖、离线可用。

- **机制**：自定义组件 `forager_panel`（见 `components/`）在 `web_server_base` 上额外注册一条
  HTTP handler，把 `web/index.html` gzip 后打进 Flash，serve 到 **`/dashboard`**。
  页面用 **ESPHome 原生 SSE 流（`/events`）** 订阅实时状态与日志，**命令**走 REST（`POST /switch/<name>/toggle`），
  **页面与数据都在 ESP32 本地**，不依赖任何 CDN/HA/N100。
- **实时日志 / 调试**：面板底部「调试」页通过 `EventSource('/events')` 订阅 `log` 事件，实时滚动显示
  ESP32 日志（485 按键 `[di]`、轮询计数 `[stat]`、MPPT 告警等），带「暂停 / 清空 / 自动滚底」。初期排查
  485 模块不稳定时，手机打开即可看日志，无需插电脑。
- **设置页**：底部「设置」页分三块——①光伏充电控制（充电输出开关、允许充电开关、充电限流滑块 0~40A、
  4 个维护按钮：远程控制/时钟同步/读参数/消音，均来自 `mppt.yaml` 已有实体）；②系统与维护（WiFi SSID/IP/信号
  显示 + 一键重启 ESP32 + 跳原生 OTA 页，来自 `system.yaml` 新增实体）；③面板偏好（日志自动滚动开关，存
  localStorage，不落 ESP32）。
- **为什么是自定义组件**：ESPHome 原生 `web_server` 的 `/` 被 `<esp-app>`（官方 Lit 前端）锁死，
  `js_include`/`css_include` 只能**叠加**在原生界面上、不能替换整页，且与 `local: true` 互斥。
  要「打开就是自己的界面 + 完全离线 + 自由布局」，唯一干净的路是外部组件自己注册路由
  （详见 [build-guide.md §6.5](../build-guide.md)）。
- **入口**：手机打开 `http://<esp32-ip>/dashboard`（兜底 AP `http://192.168.4.1/dashboard`）。
  原生 `web_server` 前端照旧在 `/`，两者并存、互不干扰。
- **实体名路由**：`web_server` 用实体的 `name`（而非 `id`）做 URL 匹配，故 `web/index.html`
  里的 `ENTITIES`/`SCENE_SENSORS`/`COULOMB_SENSORS` 记录了每个 key 的**精确中文 name**。改任何实体的 `name:`
  后，必须同步改 `web/index.html` 里的对应映射，否则该开关在面板上会读不到。
  改完可用这条命令自查「面板 ↔ 固件」是否逐字一致：
  ```bash
  diff <(grep -h 'name: "\[' relay-cabin-a-4ch.yaml relay-mid-8ch.yaml relay-mid-4ch.yaml \
         | sed 's/.*name: "//;s/".*//' | grep -vE 'DI|LED' | sort) \
       <(grep -o "domain:'switch', name:'[^']*'" web/index.html \
         | sed "s/domain:'switch', name:'//;s/'\$//" | sort) && echo '一致'
  ```
  > **命名约定（2026-10-28 调整）**：负载实体名区分**灯具朝向**，避免歧义——
  > `[额头.R1] **前射灯**`（车头朝前射灯 ×2，原名「射灯」）、
  > `[中8.Y7] **车尾灯**`（车尾灯，原名「倒车灯」——该灯**纯手动、不联动倒挡**，
  > 叫「倒车灯」易误解为自动亮）。
  > ⚠ 物理按键的 DI 名（如 `[额头.DI1] 驾驶室-射灯`）仍按**键位功能**命名，不随负载实体改名，
  > 因为按键面板上的丝印/功能就是「射灯/倒车灯」；`switch-assignment.md` 里描述硬件位置的「射灯/倒车灯」同理保留。
- **库仑计显示（2026-10-28）**：首页「能源」卡新增**剩余续航 / 剩余容量**两格；电池页新增
  **「库仑计 (TF03K)」卡片**（SOC 弧形仪表 + 电压/电流/功率/剩余容量/剩余时间 + 帧统计）。
  - **SOC 优先级**：库仑计收到帧后用其**直读百分比**；库仑计离线（`cbSoc === null`）时才回退到
    原「电压估算」（`voltToPct`，44V≈0% ~ 54V≈100% 磷酸铁锂）兜底。
  - **电流方向配色**：正 → 绿色（`good`），负 → 橙色（`warn`）。⚠ 充/放对应正负哪一侧**待实测定档**。
  - **离线提示**：未收到任何帧时，卡片底部显示「库仑计未上线」条 + `BAD=` 计数（排查接线）。
  - 实体名映射集中在 `web/index.html` 的 `COULOMB_SENSORS`，与 `pzem-tf03k.yaml` 的 8 个 `name:` 一一对应。
- **电池健康（JK 极空 BMS，2026-10-31）**：电池页新增**「电池健康 (JK BMS)」卡片**——
  汇总值 + **16 节单体 4×4 网格**（列优先，01→04 竖排）+ 最高/最低单体高亮 + 压差分级
  （`<0.02V` 绿 / `0.02~0.05V` 黄 / `>0.05V` 红）+ 充放电 MOS 状态 + 告警 + 「数据龄」。
  - **数据源尚未接通**：BMS 只能走 BLE，需独立代理 ESP32；主网关当前没有 `Bms*` 实体，
    故卡上显示「JK BMS 未上线 · 等待 BLE 代理数据」（一帧都没收到时不铺空 `--`）。
  - **与库仑计并列、不覆盖**：库仑计 TF03K 仍是**主电量来源**（硬线、离线可靠），
    BMS 的 SOC 仅作对照。BLE 掉线时只有本卡变灰，电量照常可读。
  - **实体名映射**集中在 `web/index.html` 的 `BMS_SENSORS`/`BMS_BINARY`/`BMS_TEXT`/`BMS_CELLS`
    （共 31 个），全部**只读展示**，面板不写 BMS。完整清单与固件实现要求：
    [energy/jk-bms-integration.md §四](../../energy/jk-bms-integration.md)。
  - ⚠ **`BmsFrames 有效帧数` 是必填实体**：ESPHome 只在值变化时推 SSE，电池静止时
    没有事件到达，面板就无法区分「BLE 断了」和「数值没变」。计数器每帧 +1 提供心跳。
  - 本地预览：`python3 dev-preview.py`（正常）/ `--no-bms`（未上线）/ `--bms-bad`（红色异常）
    / `--bms-na-temp`（温度报 NA）。
- **场景档位**：`light_scene`/`camp_scene`/`fan_scene` 本是 `base.yaml` 的 globals（非实体、
  REST 读不到），由 `scene-state.yaml` 用 3 个 template sensor（`SceneLight`/`SceneCamp`/`SceneFan`）
  每 1s 读出真实值，面板借此显示真实档位。
- **水位显示已移除**：面板不含水位刻度（固件暂无可读的水箱液位传感器——现用的房车水箱探头为
  模拟/机械式、读不到连续数值）。清水/灰水/黑水的**水位显示**已从面板删除；**上水泵 / 电控水阀**
  等真实 RS485 继电器开关仍保留。等换上 485 数字液位传感器（0x20 起）后，再在面板补 `sensor` 映射。

#### 页面信息架构（首页求快 / 开关页求全）

两页职责**刻意分离**，不是重复：

| 页 | 定位 | 内容 |
|----|------|------|
| **首页** | 停车后要「一眼看到、一碰就好」 | 情景模式 **2 键**（灯光/离车驻车）+ **快捷开关 8 格**（见下）+ 能源摘要卡 |
| **开关页** | 设备分散在各柜，要「全部都在、按类型找」 | 全部 **11 个可控负载**分 4 组：**照明**(5) / **通风**(2) / **水路**(2) / **负载设备**(2)，另加**能源系统**占位组 |
| **电池页** | 能源**详情** | 光伏系统 8 项（PV/电池电压、电流、功率、温度、日/累计发电）+ 库仑计详情卡（SOC 弧、帧统计排障）+ **充电趋势**（24h 折线） |

**首页快捷区布局（2026-10-30 定稿）** —— 按「每行成类」排列，扫读最快：

| 行 | 内容 | 归类 |
|----|------|------|
| 1 | 主灯 / 氛围灯 / 前射灯 | 主照明 |
| 2 | 户外灯 / 上水泵 / 后窗排扇 | 辅助照明 + 水路 + 通风 |
| 3 | DSP / 逆变器（占位） | 电气设备 |

- **为什么不把 11 个全放首页**：首页会变成「场景 + 开关 11 + 能源卡」，需滚动多屏，
  失去「一眼快控」优势。首页只留 8 格。
- **冰箱不在快捷区**：开关频率极低，留在开关页「负载设备」组即可（2026-10-28 按用户要求移出）。
- **排气扇场景卡已移除**（2026-10-30）：扇体需**手动安装到窗口**，作为「情景模式」无常驻意义。
  改为在**快捷开关**里单独控制（`fanRear`）。⚠ 固件里物理按键的三态循环（`fan_scene_next`）**仍保留**，
  只是面板不再显示该场景卡；将来装好想恢复，把按钮加回 HTML 即可（`renderScenes` 已做空值保护）。
- **逆变器用置灰占位卡**：固件无实体，放在快捷区第 3 行末尾，不可点击，见 §能源系统。
- **「负载设备」≠「能源系统」**：冰箱/DSP 是**用电器**（消耗，可直接开关）；逆变器/MPPT/行车发电是
  **能源系统**（产电/变电，功率大）。两类不能混在一组，故分组在现在就预留好。
- **通风独立成组**：原先「副驾排扇」混在电力组、「后窗排扇」混在水路组，电机类被拆到两处不合理，已归并。
- **能源卡是综合摘要**（库仑计优先、电压估算兜底），详细的光伏/库仑计/趋势数据看电池页——两层设计，不需合并。

##### 能源系统为什么是置灰占位卡

「能源系统」组目前渲染 3 张**不可点击**的置灰卡（逆变器 / MPPT / 行车发电），属于刻意的**预留**：

| 器件 | 现状 | 为什么还不能控 |
|------|------|----------------|
| 逆变器 | BOM「待购」 | 固件中尚无任何实体 |
| MPPT | 有 8 sensor + 2 开关，走**协议档** | 协议档 vs 硬件档（63A 接触器）**未实测定档**，见 [mppt-protocol.md §四](../../energy/mppt-protocol.md) |
| 行车发电（DC-DC） | 不支持 485 | **无协议可控**；输出侧接触器切换方案暂缓 |

**控制原则（[switch-assignment.md §决5](../../../04-power-system/switch-assignment.md)）**：>10A/48V 的负载，
模块 DO **只切大继电器/接触器的线圈**（mA 级），不切动力线。这三项都属该档，但**线圈由哪路 DO 驱动、
额定电流多少，尚未逐个实测定档**，所以现在仍是物理开关。

> ⚠ 占位卡故意用 `<div aria-disabled="true">` 而非 `<button>`：语义上就不可交互，
> 且其 key（`inverter`/`mppt`/`dcdc`）**不在 `ENTITIES`/`state.switches` 里**，
> 所以既不会被 SSE 状态更新影响，也不会发出任何 REST 命令。
> **定档后启用**：在 `ENTITIES` 填实体名 + 把 key 移入 `GROUPS.energy`，即可从占位变可用。

#### 本地预览（无 ESP32 时打磨页面）

页面只依赖两条通道（`GET /events` 的 SSE + `POST /<domain>/<name>/<action>` 的 REST），
语义足够简单，可以完全脱离硬件开发：

```bash
cd modules/10-smart-control/gateway/esphome/web
python3 dev-preview.py            # 打开 http://127.0.0.1:8321/dashboard
python3 dev-preview.py --no-coulomb   # 模拟库仑计未上线（验证 -- 占位与提示条）
```

`dev-preview.py` 内置全部实体名（与各 yaml 的 `name:` 一致）与假数据，模拟继电器动作、
光伏功率漂移、日志推送与心跳。**只是开发工具，不参与构建、不进固件。**
改完页面务必在这上面过一遍各页再编译，能省掉「刷进去才发现排版炸了」的来回。

#### 页面开发注意事项（踩过的坑）

- **库仑计 SOC 是小数**（如 `78.19`），`.gauge .num b` 用 `.wide` 小一号字号，否则数字溢出弧内。
- **日志等级解析**必须用 `^(?:\[[\d:.]+\])?\[([EIWVD])\]`：若用 `\[([A-Z])\]` 裸匹配，
  会把时间戳/正文里的字母误判成等级，导致整行染色错误。
- **场景卡是只读的**（档位由物理按键驱动 globals，面板改不了），故不加 `cursor:pointer`/
  按压反馈，并带 `readonly` 角标，避免用户以为点了能切场景。
- **分组网格列数自适应**：4 个开关用 2×2（3 列会剩一个孤格，看着像页面坏了）。
- **长文本值**（如「MPPT充电中」）加 `ellip` 类单行省略，否则会把能源卡撑高、网格错位。

### 485 地址占用

> **2026-10-30 重编：只动继电器模块，能源设备不动。以 0x05 为分界线。**

| 地址 | 设备 |
|------|------|
| **0x01** | 驾驶室 A（4DI+4DO 5A，额头柜） |
| **0x02** | 驾驶室 B（4DI+4DO 5A，额头柜，场景键） |
| **0x03** | 8DO（额头柜，场景双色 LED） |
| 0x04 | （空）额头柜预留 |
| **0x05** | **分界线（不分配）** |
| **0x06** | 中门 8 路（8DI+8DO 10A） |
| **0x07** | 中门 4 路（4DI+4DO 5A） |
| 0x08~0x0F | （空）中门预留 |
| 0x10 | MPPT（易科 Fcu，**固件已就绪**，见 `mppt.yaml`） |
| — | **TF03K 库仑计**（无地址、非 Modbus、19200 独立 UART，不在此总线） |
| 0x20+ | 485 传感器（建议） |

> **加模块规则**：额头往后排 0x04，中门往后排 0x08、0x09…，**永不重编**。
> 16DO 库存备用（可占 0x08，或更低优先级的空位）。

### 写帧方式

通道动作只需给一条帧，DE 时序由 `rs485_write` 统一处理：

```yaml
on_turn_on:
  - script.execute:
      id: rs485_write
      frame: [0x02, 0x05, 0x00, 0x00, 0xFF, 0x00, 0x8C, 0x09]
```

帧格式 = `站号 FC 线圈地址高 低 值高 值低 CRC低 CRC高`（Modbus RTU，CRC16-Modbus 低字节在前）。
线圈地址：**通道 N = 地址 N-1**（Y1=0x0000）。

## 独立固件（另一台 ESP32）

| 文件 | 用途 | 说明 |
|------|------|------|
| `ble-proxy.yaml` | **BLE 蓝牙代理**（收温湿度等 BLE 广播转 HA） | **独立一台 ESP32**，不并入 prod。理由与实测资源见 [sensors/ble-sensors.md](../../sensors/ble-sensors.md) |

> 为什么独立：BLE 协议栈约需 1.2MB Flash。并入主网关会让 Flash 从 53% 涨到 **75%**（偏紧），
> 且 BLE 故障会牵连承担安全关键自动化的主网关。独立后主网关保持 53%，故障隔离。

## ⚠ 波特率（MPPT 的硬前置）

当前全部固件为 **38400**（继电器模块出厂默认，桌面联调阶段）。全车终局为 **9600**
（MPPT 最高只支持 9600，见 [build-guide.md §4.7](../build-guide.md)）。

**MPPT 一挂上总线，就必须先完成 §4.7 改造**：4 个继电器模块改 9600 + 固件 4 处
`baud_rate` 改 9600。否则 MPPT（只有 9600）与继电器模块（38400）在同一条总线上
互相乱码，两边都用不了。

> ⚠ 波特率代码两家不同：**MPPT 的 9600 = 代码 4**（`0xDE` 群控或 LCD 设），
> **继电器模块的 9600 = 代码 1**（FC06 写 0033H）。

## MPPT 固件说明（mppt.yaml）

- **轮询**：每 10s 发 `0xA3/02` 查实时数据（协议要求间隔 ≥1s），38 字节应答
- **解析**：`solar_read` 每 100ms 扫 UART 缓冲，按「地址 0x10 + 命令码 + 已知帧长」
  定位并做 **CRC + 帧长双校验**，通过后交给 `solar_parse` 按偏移发布
- **实体**：8 路 sensor（PV/电池电压、充电电流、发电功率、日/总发电量、控制器/电池温度）
  + 2 路 text_sensor（充电状态、告警）+ 充电输出/允许充电开关 + 充电限流 number
- **维护按钮**：设为远程控制 / 时钟同步 / 读设置参数 / 蜂鸣器消音
- **本地自动化**：见 [energy/mppt-protocol.md §三](../../energy/mppt-protocol.md)

> **待实测定档**（见 mppt-protocol.md §四）：关闭 DC 输出后控制器待机电流是否归零、
> 485 是否仍响应——决定走「协议档」还是「硬件档（加 63A 接触器，额头.R6 驱动）」。
> 本文件目前实现了**协议档**的监控与控制骨架；定档后如需硬件档再补 R6 驱动逻辑。

### 充电趋势（SolarTrend）——MPPT 本身没有历史数据

> ⚠ **重要事实**：MPPT 只有 `日发电量`(0x20-0x23，0 点清零) 和 `总发电量`(0x24-0x27，累计不清零)
> 两个**累计值**，**没有任何历史曲线/分时数据**。想知道「上午10点到12点发了多少」只能自己攒。

因此固件在 ESP32 本地维护一个**环形缓冲**（`mppt.yaml` 的 `trend_sample` 脚本）：

| 项 | 值 |
|----|-----|
| 采样间隔 | 5 分钟（`interval: 5min` + `delay: 30s` 错开 10s 轮询） |
| 容量 | **288 点 = 24 小时**，`std::array<uint16_t, 288>` = 576 字节 |
| 内容 | 每次记一个**功率(W)**；MPPT 离线时记 0（曲线归零即代表夜间/离线） |
| 传输 | 编码成 `"v1:<count>:<idx>:<base64>"` 经 text_sensor 推送上 SSE |

- **为什么要 base64**：SSE 只能传字符串，无法直传数值数组。uint16 小端打包后
  base64 仅 **768 字符（0.75 KB）**，对 web_server 负担很轻。
- **时间正序**：固件输出前已按「最旧→最新」展开（环形回绕时从 `idx` 起读），
  面板拿到即可直接画，**无需处理回绕**。
- **⚠ `std::vector` 会编译失败**：vector 的 `initial_value` 会让 `GlobalsComponent`
  构造函数产生重载歧义，必须用 `std::array<uint16_t, 288>`（已实测）。
- **⚠ 重启即清零**（纯 RAM）。长期趋势待 N100/HA + InfluxDB 就位后另做。
  TODO 里「N100 部署 PVE/HA」完成后可考虑把数据转存过去。
- **面板侧**：电池页「充电趋势」卡用**纯内联 SVG** 手绘折线（`drawTrend()`），
  零依赖、离线可用。无数据时显示空态说明，不会让人误以为坏了。

#### MPPT 配置项为什么不加光控/时控

协议确实支持这些可配置项（见 [mppt-protocol.md](.../../../energy/mppt-protocol.md)）：

| 代码 | 参数 | 为什么**不**放面板 |
|------|------|---------------------|
| 0x0C | DC 输出控制方式 | **与远程控制互斥**（见下） |
| 0x22 | 浮充电压 | 电池安全参数，误设伤电池 |
| 0x23/0x26 | 低压保护/恢复 | 同上 |
| 0x27/0x28 | 过压保护/恢复 | 同上 |
| 0x29/0x2A | 光控开关阈值 | 需实测定档 |
| 0x2B/0x2C | 光控延时 | 同上 |
| 0x2D~0x30 | 时控 1/2 开关时间 | 同上 |

> **⚠ 关键限制：`0x0C` 只能取一个值**
> —— `0=关闭 / 1=自动 / 2=时控 / 3=光控 / 4=远程控制`。
>
> 当前系统用的是 **`4=远程控制`**，面板上的「充电输出」开关才有效。
> **一旦设成光控或时控，远程开关就失效了**（控制权交给控制器自己）。
> 所以这不是"多加几个配置项"，而是**切换整个系统的控制权归属**——
> 需要先想清楚"到底谁管充电"，再决定是否提供这些开关。
>
> 同理，浮充/过压/低压等**电池保护参数**建议一次性在 MPPT 本体上设好，
> 不放面板，避免手机误触造成电池损坏。

## 库仑计固件说明（pzem-tf03k.yaml）

**TF03K 库仑计**，2026-10-28 新增。

- **接口**：独立**第二路 UART**（`coulomb_uart`，**19200**，TX=GPIO5 / RX=GPIO4，实际只用 RX）
- **协议**：私有主动上报，**16 字节/次，1 次/秒**，无地址、非 Modbus、**8 位累加和**（非 CRC16）
- **只收不发**：TF03K 的 RXD 无接收功能，固件不含任何写帧，**不调用 `rs485_write`、不做 DE 切换**
- **帧解析**：`coulomb_read` 每 200ms 扫 UART 缓冲 → 找 `0xA5` 帧头 → 验累加和 → 解析发布；
  残帧跨 tick 保留（与 `base.yaml` 的 `read_upload` 同思路）
- **实体**：6 个 sensor（SOC%/电压/剩余容量/电流/剩余时间/功率）+ 2 个诊断计数

### 帧结构（16 字节）

| 字节 | 内容 | 换算 |
|------|------|------|
| 1 | 帧头 `0xA5` | — |
| 2 | 电量百分比 | 直取 % |
| 3-4 | 电压 | 大端 16，÷100 → V |
| 5-8 | 剩余容量 | 大端 32，mAh ÷1000 → Ah |
| 9-12 | 电流 | 大端 32 有符号（补码），mA ÷1000 → A |
| 13-15 | 剩余时间 | 大端 24，秒 |
| 16 | 校验和 | 前 15 字节 8 位累加和 |

### ⚠ 接线与总线隔离

- **严禁与 9600 Modbus 总线同挂**：波特率、协议、方向、寻址全都不同。
- TF03K RS485 A/B → MAX3485 → ESP32 RX；**MAX3485 的 DE/RE 接 GND（常接收）**，不要接 GPIO。
- TF03K **内部已含 120Ω 终端电阻**；网关侧 MAX3485 若也带终端，仅在总线两端各保留一颗、避免过量匹配。
- **待实测确认**：电流正负方向（协议只写"负值为补码"，未说明充/放哪边为正）。

### 关于 UART 列表化（base.yaml 已改）

引入第二路 UART 时发现：ESPHome packages 合并时**映射写法与列表写法不能共存**，
若 base 用 `uart:` 映射、本文件用 `uart:` 列表，base 那一路会被覆盖（报 `Couldn't find ID 'rs485_bus'`）。
故 `base.yaml` 的 uart 已统一改为**列表形式**（**只改写法，485 引脚/波特率不变**，行为与改动前一致）。
实测 `esphome config` + `esphome compile` 通过，两路并存：`rs485_bus` 38400 / `coulomb_uart` 19200。
